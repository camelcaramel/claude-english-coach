사용자가 영어로 쓴 요청: $ARGUMENTS

아래를 순서대로 한다.

**1단계는 무조건 먼저 한다.** 요청이 모호해도, 작업할 코드가 없어도, 되물어야
하는 상황이어도 — 교정 블록부터 출력하고 그 다음에 묻는다. 이 커맨드를 쓰는
이유가 교정이라서, 교정을 건너뛰면 커맨드가 아무 일도 안 한 것이 된다.

## 1. 교정본을 먼저 보여준다

원어민 엔지니어가 코딩 에이전트에게 칠 법한 영어로 고친다. 문법만이 아니라
관용 표현까지 — 뜻은 통하지만 어색한 표현도 자연스럽게 바꾼다.

정확히 이 형식으로, 다른 말은 붙이지 않는다:

```
✎ <사용자가 쓴 그대로>
→ <교정본>
  · <표현> — <왜 이렇게 쓰는지 한국어로 한 줄>
  · <표현> — <한국어로 한 줄>
```

표현은 1~3개. 다시 쓸 수 있는 패턴을 고르고 `~` 로 갈아끼우는 자리를 표시한다
(`guard against ~` 은 익힐 값이 있고 `design system` 은 없다).
고칠 게 없으면 `→` 줄에 `그대로 좋습니다` 라고 쓰고 표현만 짚는다.

## 2. 적립한다

Bash 로 한 번 실행한다. `--phrase` 는 표현 개수만큼 반복한다.

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/log-correction.js" --data "${CLAUDE_PLUGIN_DATA}" --raw "<사용자가 쓴 그대로>" --fixed "<교정본>" --phrase "<표현>|<한국어 뜻>|<그 패턴을 쓴 다른 짧은 예문>"
```

`--data` 를 빼지 않는다. 빼면 기록이 엉뚱한 곳에 쌓여 `/en-review` 에 안 잡힌다.

값 안에 큰따옴표를 넣지 않는다 — 필요하면 작은따옴표로 바꿔 쓴다.
`|` 는 구분자이므로 값 안에 쓰지 않는다.
JSON 을 명령줄에 싣지 않는다. Bash 도구가 중괄호와 따옴표가 같이 든 명령을
차단하므로 반드시 실패한다.

스크립트 출력은 사용자에게 보여주지 않는다. 실패해도 그냥 넘어간다.

## 3. 교정된 요청을 실제로 수행한다

여기서 멈추지 않는다. 교정본이 뜻하는 작업을 이어서 그대로 진행한다.
사용자의 원문이 어설퍼도 **교정본의 의도**를 따른다.

의도가 두 갈래로 읽히거나 작업할 대상을 못 찾으면, 1·2단계를 마친 뒤에 묻는다.
묻느라 교정을 생략하지 않는다.
